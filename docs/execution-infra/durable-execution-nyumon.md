# durable execution 入門 — AI エージェント時代の実行基盤

> 対象: 「Temporal という名前は見たが、何を解いているのか分からない」人
> 前提: [iPaaS 入門](./ipaas-nyumon.md) の §15（AI 時代のデータ連携）の続き
> ゴール: 何を保証し、何を保証しないかを正確に言えるようになる

---

## 0. なぜこれが要るのか — 結論から

> **一番危険なのは、失敗することではない。中途半端に成功することである。**

```
請求書を作成    → ○ 成功
台帳を更新      → ✕ ここで落ちた
経理へ通知      → ─ 未実行
```

この状態が残ると、**請求書は存在するのに台帳には載っていない**。そして誰も気づきません。

失敗ならリトライすればいい。エラーが出れば気づける。**中途半端な成功は、静かにデータの整合性を壊します。**

エージェントが1分間に何十件も判断を下す世界では、これが常時発生します。人間が気づいて直す運用は成立しません。durable execution は、この一点を解くための仕組みです。

---

## 1. 導入の目的

優先度順に4つです。**この順序が重要です。**

| # | 目的 | 内容 |
|---|---|---|
| **1** | **完遂させる** | 途中で死んでも最後まで到達させる |
| **2** | **副作用を一度だけにする** | 請求書が2枚できない |
| **3** | **長時間の待機を可能にする** | 承認待ちで3日止まってもコストが増えない |
| 4 | トークンを節約する | 結果として付いてくる |

### よくある誤解 ①

> **「AI に無駄なステップを実行させず、トークンを節約する仕組み」**

半分正しいのですが、**目的の順序が逆**です。トークン節約は4番目、しかも結果であって目的ではありません。

もし目的がそれだけなら、LLM レスポンスのキャッシュで足ります。しかし——

| | キャッシュ | durable execution |
|---|---|---|
| 何をキーにするか | **入力の内容** | **実行のどの地点か** |
| 中断した処理の再開 | できない | **できる** |
| 3日待つ | できない | **できる** |
| ツール実行の副作用 | 防げない | **一度だけにできる** |
| **まだ実行していないステップ** | 関知しない | **必ず実行する** |

最後の行が決定的です。**キャッシュは「二度やらない」しか面倒を見ません。durable execution は「必ず最後までやる」も面倒を見ます。**

## 2. 定義

> **durable execution（耐久実行）= 実行の進捗そのものを永続化し、プロセスが死んでも続きから再開できるようにする仕組み**

やっていることは3つだけです。

1. コードの進行を**イベント履歴**として外部に記録する
2. クラッシュしたら、**コードを最初から再実行する**
3. ただし履歴に結果が残っているステップは、**実行せずに記録済みの結果を返す**

### よくある誤解 ②

> **「ワークフローを履歴として残すことで、データの整合性を保つ仕組み」**

保つのは**実行の進捗**であって、**データの正しさではありません**。

「どこまでやったか」を失わないことは保証しますが、「そのデータが正しいか」は保証しません。データの正しさは source of truth の設計の領分です（→ iPaaS 入門 §4.3）。

## 3. 前提知識 — 決定論的 / 非決定論的

### 3.1 定義

> **決定論的** = 同じ入力を与えたら、**必ず**同じ出力が返る
> **非決定的** = 同じ入力でも、**違う出力が返りうる**

| 決定論的 | 非決定的 |
|---|---|
| 電卓に `2+3` と入れる | サイコロを振る |
| 辞書で「犬」を引く | 時計を見る |
| ソートする | 天気を聞く |

```go
// 決定論的 — 何度呼んでも同じ
func add(a, b int) int { return a + b }

// 非決定的 — 呼ぶたびに違う
func stamp() time.Time { return time.Now() }
```

### 3.2 非決定性の源は「外の世界」

**関数の中だけで完結する計算は決定論的。外に触った瞬間に非決定的になります。**

- 時刻（`time.Now()`）
- 乱数（`rand`）
- ネットワーク（HTTP、DB）
- ファイルシステム
- goroutine のスケジューリング
- **map の反復順**（Go は意図的にランダム化している）
- **LLM**

### 3.3 決定論的 ≠ 予測可能

| | 意味 |
|---|---|
| **決定論的** | 同じ入力なら同じ結果に**なる**（再現できる） |
| **予測可能** | 実行前に結果が**分かる** |

durable execution が要求するのは**前者だけ**です。

LLM が何と答えるかは事前に分かりません（予測不可能）。しかし**一度答えが記録されれば固定された入力になる**ので、以降は何度リプレイしても同じ経路をたどります（決定論的）。

Temporal の表現を借りると:

> **実行においては決定論的だが、事前に決まってはいない。**

## 4. 仕組み — リプレイ

### 4.1 動き

```
【初回実行】
  Step1 請求書作成  →  Step2 Slack通知  →  Step3 台帳更新
  実際に実行            実際に実行           ここでクラッシュ
      ↓                    ↓
  ┌──────────────────────────────────────────┐
  │ イベント履歴：Step1 完了 ／ Step2 完了      │
  └──────────────────────────────────────────┘
      ↓                    ↓
【再起動後】
  Step1              →  Step2            →  Step3
  履歴から結果を返す      履歴から結果を返す     ここから実際に実行
```

書く側から見ると、こう見えます。

```go
acct.CreateInvoice(...)   // ← ただの関数呼び出しに見える
slack.Post(...)           // ← が、結果は永続化されている
ledger.Update(...)        // ← クラッシュしてもここから再開する
```

**進捗管理のコードが一行もありません。** これが売りです。

### 4.2 なぜ非決定性が邪魔になるのか

具体例が一番早いです。

```go
if time.Now().Hour() < 12 {
    午前の処理()
} else {
    午後の処理()
}
```

| | 時刻 | 選ぶ枝 | 結果 |
|---|---|---|---|
| 初回実行 | `time.Now()` → 11:59 | 午前の処理 | 履歴に記録 |
| リプレイ | `time.Now()` → 12:01 | **午後の処理** | **履歴と不一致 → 壊れる** |
| リプレイ（修正後） | `workflow.Now()` → 11:59 | 午前の処理 | 履歴と一致 |

11:59 に動き始めて 12:01 に再開すると、**同じコードなのに違う枝を選んでしまう**。すると履歴と食い違ってリプレイが続行できません。

`workflow.Now(ctx)` は**記録された時刻**を返すので、再開しても 11:59 のままです。

### 4.3 よくある誤解 ③ — リプレイは「再現」ではない

> **「時刻はホワイトボックスだから戻せる。LLM はブラックボックスだから無理では？」**

**リプレイは再現していません。記録を読み直しているだけです。**

`workflow.Now(ctx)` が 11:59 を返せるのは、時計の仕組みを理解しているからではありません。**11:59 という値をメモしたから**です。

LLM も同じです。「エスカレーション」という文字列をメモしたから読み直せる。**モデルの中身を理解する必要はありません。**

> AWS Durable Functions のドキュメント: 非決定的なコードを step で包むことが、耐久実行を決定論的にする主要な方法。step にカプセル化すると、リプレイ時に異なる結果を生成しないので決定論的になる。

**ホワイトボックスかブラックボックスかは、この機構には関係ありません。**

### 4.4 むしろブラックボックスのほうが安全という逆説

**LLM が非決定的なことは誰もが知っています。だから必ず Activity に包まれる。見落とされません。**

危ないのは「決定論的に見えるが、実はそうでない」ものです。

| 一見決定論的 | 実際は |
|---|---|
| `for k := range m` | Go は反復順を意図的にランダム化している |
| goroutine の完了順 | スケジューラ次第 |
| ライブラリの内部ソート | バージョンアップで順序が変わりうる |
| 集合の列挙順 | 実装依存 |
| 浮動小数点の集約順 | 並列化すると変わる |

**これらは黙って壊れます。** テスト環境では100回通って、本番の高負荷時にだけリプレイが失敗する。

> **ブラックボックスだと分かっているものは扱いやすい。厄介なのは、ホワイトボックスのふりをしている非決定性のほう。**

### 4.5 ただし1点、確かに違うところ

| | 記録する | 固定する（再現する） |
|---|---|---|
| `time.Now()` | できる | **できる**（テストでモックすれば同じ値） |
| 乱数 | できる | **できる**（シード固定で同じ列） |
| **LLM** | できる | **できない** |

`temperature=0` にしても、推論のバッチングやハードウェア差でビット単位の再現はできません。

**LLM は「記録する」以外の道が最初から閉ざされている。** 時刻や乱数には2本の道があるのに、LLM には1本しかない。

ただし durable execution が選んでいるのは、もともと「記録する」ほうの道です。**だから LLM でも同じ機構がそのまま使えます。**

## 5. 設計の肝 — Workflow と Activity の分離

### 5.1 役割分担

| | Workflow | Activity |
|---|---|---|
| 役割 | **段取りを決める** | **外の世界に触る** |
| 決定論 | **必須** | 不要 |
| 副作用 | 禁止 | OK |
| リトライ | – | 組み込み |
| 例 | 「請求書を作り、次に通知する」 | `POST /invoices` を叩く |

```go
// Workflow — 段取りだけ。外の世界に触らない
func InvoiceWorkflow(ctx workflow.Context, dealID string) error {
    ctx = workflow.WithActivityOptions(ctx, workflow.ActivityOptions{
        StartToCloseTimeout: time.Minute,
        RetryPolicy: &temporal.RetryPolicy{MaximumAttempts: 5},
    })

    var invID string
    if err := workflow.ExecuteActivity(ctx, CreateInvoice, dealID).Get(ctx, &invID); err != nil {
        return err
    }
    return workflow.ExecuteActivity(ctx, NotifySlack, invID).Get(ctx, nil)
}

// Activity — ここでだけ外を叩く。落ちてもリトライされる
func CreateInvoice(ctx context.Context, dealID string) (string, error) {
    return freeeClient.CreateInvoice(ctx, dealID)  // 普通のGoコード
}
```

`RetryPolicy` の1行が、iPaaS の実行基盤が GUI の裏でやっていたリトライに相当します。**iPaaS が隠していたものが、ここでは明示的な設定として出てきます。**

### 5.2 Workflow の中で禁止されるもの

| 禁止 | 代わりに |
|---|---|
| `time.Now()` | `workflow.Now(ctx)` |
| `time.Sleep()` | `workflow.Sleep(ctx, d)` |
| `rand` | `workflow.SideEffect` |
| `go func(){}` | `workflow.Go(ctx, ...)` |
| map の反復 | ソートしたスライス |
| HTTP / DB 呼び出し | **Activity に追い出す** |

**「3日待つ」がコスト0で書けるのはこの仕組みのおかげです。** `workflow.Sleep(ctx, 72*time.Hour)` と書けば、その間ワーカーは何も抱えません。人間の承認待ちがまさにこれです。

## 6. ステップとは何か

### 6.1 範囲は開発者が決める

**ステップは LLM 呼び出しに固定されていません。** `ExecuteActivity` で包んだ関数、それがステップです。

| 粒度 | 例 |
|---|---|
| 粗い | 「エージェントを1周まわす」（LLM 呼び出し＋ツール実行＋統合をまとめて1ステップ） |
| 細かい | 「LLM に聞く」「ツールを叩く」をそれぞれ別ステップ |

細かくすれば失う作業は少なくなりますが、履歴への書き込みが増えます。

### 6.2 よくある誤解 ④ — 「ステップは出力が終われば完了」

> **「LLM が出力を始めてから出力を終えるまでがステップ？」**

**惜しいのですが、終わりの定義がずれています。**

```
┌──────────────┬──────────────┬──────────────┬──────────────┐
│ 呼び出し開始   │ LLMが出力中   │ 出力完了      │ 履歴に記録    │
│              │              │ 結果は手元    │ ここで確定    │
└──────────────┴──────────────┴──────────────┘              │
 └──────── この区間で落ちたら、まるごとやり直し ────────┘
```

**LLM が答え終わって文字列が手元にあっても、まだ安全ではありません。** 履歴に書き込む前にワーカーが死ねば、記録は存在せず Activity は再実行されます。**トークン代を払って得た答えが、そのまま捨てられます。**

この「結果は持っているのに記録できていない」区間は、分散システムで昔からある問題そのものです。

### 6.3 記録前に落ちたらどうなるか

| 状況 | 挙動 |
|---|---|
| LLM 応答が完了し、履歴に記録済み | **記録を読む → 必ず同じ答え** |
| 応答の途中、または記録前に落ちた | **モデルに聞き直す → 違う答えになりうる** |

**保証は「記録された結果、または新規実行」であって、「同じ結果」ではありません。**

業界もこの部分は解こうとせず割り切っています。LLM ストリーミング中のような mid-step のチェックポイントは、不完全なステップはどのみち再実行が必要なので複雑さの割に利益が少ない、とされています。

**なぜそれで許されるのか**

1. 失われるのは1ステップ分だけ。100ステップ中47番目なら、46番目までの記録は生きている
2. 多くのエージェントステップは「同じ文脈への新しい判断」なので、違う答えでも有効
3. 本当に危険なのは**副作用が先に出たケース**（ツール呼び出しを発行した直後、記録前に落ちる）→ 冪等キーで潰す

3点目のために、実務では**「決める」と「やる」を別ステップに分けます**。判断を先に記録してから行動する。

## 7. 保証されること・されないこと

### 7.1 よくある誤解 ⑤ — 「LLM を決定論的にする」

**しません。LLM は最後まで非決定的なままです。**

> **LLM を決定論的にするのではなく、LLM の非決定性が「ワークフローの再実行」に伝播しないようにする。**

| 対象 | 決定論的か |
|---|---|
| LLM という関数そのもの | **非決定的のまま。何も変わらない** |
| ワークフローのリプレイ | **決定論的にできる** |

サイコロで言えば——**サイコロは相変わらずランダム**です。ただ一度振った目をメモしておけば、そのメモを読む限り話は何度でも同じになる。**サイコロが変わったのではなく、メモを読んでいるだけ。**

> **非決定性を消すのではなく、一度きりに閉じ込める。**

### 7.2 保証の範囲

| 状況 | 同じ結果になるか |
|---|---|
| 同じ run の中で、記録済みのステップをリプレイ | **○ 必ず同じ** |
| 同じ run の中で、記録前に落ちたステップ | ✕ 聞き直すので変わりうる |
| 別々の run（ワークフローを2回起動） | ✕ まったくの別物 |
| 同じ入力で明日また実行 | ✕ 別の run なので変わりうる |

**守るのは「1回の実行を最後まで完遂させること」だけ**です。「同じ入力なら明日も同じ答え」は保証しません。

### 7.3 冪等性は依然として必要

**Activity は at-least-once です。**

`POST /invoices` が成功した直後にネットワークが切れたら、呼び出し側は成功したか分かりません。リトライすれば二重になります。冪等キーは `(workflow_id, step_id)` から導出するのが定石です。

| 要件 | durable execution が自動でくれるか |
|---|---|
| 監査ログ | **◎ くれる** |
| リトライの耐久性 | **◎ くれる** |
| 冪等性 | **✕ 設計事項** |
| ロールバック | **✕ 補償処理を自分で書く** |

ただし「どこまで進んだか」が確実に分かるので、**補償処理を書けるようになる**のが大きい。

## 8. AI エージェントへの適用

### 8.1 よくある疑問 ⑥ — ワークフローは誰が決めるのか

> **「人間があらかじめ与えるのか、AI が全て決めるのか。後者なら決定論的にできないのでは？」**

**答えは「両方」です。層が違います。**

```
【人間が書く：地図（コード）】実行前に固定される
  ┌──────────────┐  ┌──────────────────┐  ┌────────────────────┐
  │  ループの形   │  │  使えるツール一覧  │  │  上限・ガードレール  │
  └──────────────┘  └──────────────────┘  └────────────────────┘

【AIが決める：経路】実行してみるまで分からない
  ┌──────────────┐  ┌──────────────────┐  ┌────────────────────┐
  │ 1. 検索する   │→ │ 2. 要約する       │→ │ 3. 承認を求める      │
  └──────────────┘  └──────────────────┘  └────────────────────┘
     経路は一手ずつ履歴に記録され、リプレイでは聞き直さない
```

### 8.2 経路は最初にまとめて決まらない

**エージェントは計画を先に全部立ててから実行するわけではありません。**

```
LLMに聞く「次は何をする？」 → 「検索して」 → 記録 → 検索を実行 → 記録
LLMに聞く「結果を見て、次は？」 → 「要約して」 → 記録 → 要約を実行 → 記録
LLMに聞く「次は？」 → 「人間の承認を取って」 → 記録 → 承認待ちへ
```

**「ワークフローが決まった瞬間」は存在しません。** 一手指すごとに次が決まる。将棋と同じです。

だから記録されるのは「計画」ではなく「**指した手の列**」。リプレイのときは手を指し直すのではなく**棋譜を読みます**。

### 8.3 コードで見ると

```go
// このループは人間が書く。固定。決定論的
for i := 0; i < maxSteps; i++ {
    var next Decision
    // LLMへの問い合わせ = Activity。結果は記録される
    workflow.ExecuteActivity(ctx, AskLLM, history).Get(ctx, &next)

    if next.Done { break }

    var result string
    // ツール実行 = Activity。結果は記録される
    workflow.ExecuteActivity(ctx, next.Tool, next.Args).Get(ctx, &result)
    history = append(history, result)
}
```

**`for` も `if` も人間が書いています。** LLM が変えられるのは `next` の中身だけ。そして `next` は毎回記録される。

だからリプレイ時、このコードは同じ `next` を読み、同じ `if` を通り、同じツールを呼びます。**コードは決定論的、経路は記録済み。**

### 8.4 エージェントが越えられない一線

| AI にできること | AI にできないこと |
|---|---|
| ツール一覧から選ぶ | 新しいツールを生やす |
| 呼ぶ順番を決める | ループの構造を変える |
| 引数を組み立てる | 上限を越える |
| 早期終了を判断する | ガードレールを外す |

もしエージェントが任意のコードを生成して実行できてしまうと、**次回そのコードが存在しないかもしれない**ためリプレイは成立しません。

コード生成エージェントの場合も、生成されたコードは**データとして記録**され、Activity の中で実行されます。ワークフローの構造自体は変わりません。

### 8.5 まとめ

| 何が | 誰が決める | いつ決まる | 決定論的か |
|---|---|---|---|
| ワークフローの**定義**（コード） | 人間 | デプロイ時 | **○ 固定** |
| ワークフローの**経路** | AI | 実行時、一手ずつ | ✕ ただし記録される |
| ワークフローの**リプレイ** | — | 復旧時 | **○ 記録を読むので再現** |

> **人間が可能性の空間を定義し、AI がその中の一本の道を選び、durable execution がその道を記録して二度と選び直させない。**

## 9. なぜ AI 時代に注目されたのか

重要度順に5つです。

### 9.1 LLM の判断を「もう一度聞く」わけにいかない

**これが本質です。**

エージェントのワークフローは非決定性の塊です。LLM の出力、タイムスタンプ、乱数、検索結果、ネットワーク応答、ポリシー判断、ツールの結果。**LLM 呼び出しをリプレイして同じイベントのふりをすることはできません。**

> モデルが「この返金はエスカレーションすべき」と判断したら、その判断は記録されたワークフロー状態になるべき。復旧はその永続化された判断から再開すべきで、モデルに聞き直して別の答えを受け取ってはいけない。

これが、**エージェントが障害後に自分の履歴を書き換えてしまうこと**を防ぎます。

### 9.2 合成的な信頼性が崩れる

各ステップが99%でも、5ステップで95%、10ステップで90%。実際のエージェントはもっと長い。**100ステップ中47番目で死んだとき、48番目から再開するのか1番目からやり直すのか。**

### 9.3 実行が長すぎてリクエスト/レスポンスに収まらない

デモ環境では優秀に見えるエージェントが、処理が数日かかり API がタイムアウトし人間の承認が必要な現場に置かれると崩壊する——これが「デモとのギャップ」と呼ばれています。

エージェントは、ユーザーの依頼で起動し、数時間から数日停止し、イベントを待ち、Webhook で再開し、承認を求め、失敗した外部呼び出しをリトライし、完了済みの作業の繰り返しを避け、実世界のプロセスが終わるまで続く必要がある。

人間の承認待ちを signal パターンで実装すると、**待機中のコストが60〜80%下がる**という報告もあります。

### 9.4 トークンを二度払わない

API 呼び出し、DB 書き込み、LLM 呼び出しはリプレイ中に繰り返されません。**エージェントを最初からやり直すと、それまでのトークン代を全部払い直す**ことになります。

### 9.5 監査 — ただしトレースとは違う

**トレースは説明のためのもので、復旧のためのものではありません。**

> トレースは何が起きたかを説明できるが、耐久ジャーナルは何をリプレイしてよいか、スキップしてよいか、補償すべきか、再開すべきかを判断しなければならない。

観測ツールを入れても durable execution の代わりにはなりません。

### 9.6 市場の反応

Temporal は2026年2月17日に**50億ドル評価で3億ドルを調達**。クラウド上の累計アクション実行数は9.1兆、**うち1.86兆が AI ネイティブ企業**によるもの。LangGraph、Pydantic AI、OpenAI Agents SDK はいずれも耐久実行を第一級の機能として採用しており、**もはやオプションではなくベースライン要件**になったことを示しています。

顧客に OpenAI、Snap、Netflix、JPMorgan Chase。

## 10. 製品の地図

| 製品 | 特徴 |
|---|---|
| **Temporal** | 最も成熟。**Go 製で Go SDK が第一級**。長時間ワークフロー向き |
| **Restate** | 軽量。`ctx.run()` ごとにジャーナルするので、アプリコード側に冪等キーが不要 |
| **Inngest** | イベント駆動寄り。Webhook / キュー起点 |
| **DBOS** | Postgres に状態を持つ。軽量 |
| **Hatchet** | 通常タスクは at-least-once なので冪等性が必要 |
| **AWS Durable Functions** | マネージド。step でラップする方式 |

主要な実装方式は2つです。

| 方式 | 内容 | 採用 |
|---|---|---|
| **ジャーナルベースのリプレイ** | 完了ステップを記録し、クラッシュ時に再生 | Temporal、Restate |
| **データベースへのチェックポイント** | 各ノード後に状態を永続化 | LangGraph、DBOS |

## 11. 落とし穴

### 11.1 バージョニング（最大の痛点）

**実行中のワークフローがある状態でコードを変えると、リプレイ時にコマンド列が食い違って壊れます。**

デプロイ前に**リプレイテスト**で非決定的な変更を検出し、互換性を確認するのが定石です。過去の履歴を JSON で落として、新しいコードで再生してみる。

> **「実行中の処理があるコードは気軽に変えられない」** — 普通のワーカーにはない制約です。導入時に一番効いてきます。

### 11.2 解決しないもの

- **ハルシネーション**
- **暴走ループ**
- **eval のドリフト**
- **ストアレベルの災害復旧**

**「失敗しても壊れない」は手に入りますが、「正しい判断をする」は手に入りません。**

## 12. iPaaS との関係

### 12.1 3つの保証と担い手

| 何を保証するか | 誰が |
|---|---|
| **データの正しさ** | 人間の設計 ＋ iPaaS（source of truth の設計） |
| **実行の完遂** | **durable execution**（リプレイと冪等性） |
| **判断の正しさ** | **誰も保証しない**（eval と人間のレビュー） |

**AI エージェント時代に durable execution が必要なのは、真ん中の層が急に難しくなったからです。**

人間が操作していた頃は、実行の完遂を人間が見張っていました。「あれ、通知が来ないな」と気づいて再実行する。**エージェントが1分間に1000件の判断を下す世界では、その見張りが成立しません。**

### 12.2 iPaaS と durable execution の使い分け

| | iPaaS | durable execution |
|---|---|---|
| 書き方 | GUI | **コード** |
| レビュー | 画面を見る | **git diff** |
| 得意 | 決まった連携の反復 | **長時間・分岐の多い処理** |
| 人間の承認待ち | 別製品 | **標準機能** |
| コネクタ | 1000種類付属 | **自分で書く** |
| 適する相手 | SaaS 群 | **自社ロジック・エージェント** |

**相互に補完します。** コネクタの資産は iPaaS が強く、実行制御は durable execution が強い。

現実的な構成は**エージェント → durable execution（実行の耐久性）→ iPaaS または直接 API（相手への接続）** という積み方です。

## 13. つまずきポイント一覧

理解の途中で引っかかりやすい箇所をまとめます。

| # | 誤解 | 正しくは |
|---|---|---|
| ① | トークン節約が目的 | **完遂させることが目的。** 節約は結果 |
| ② | データの整合性を保つ仕組み | **実行の進捗**を保つ。データの正しさは別領域 |
| ③ | リプレイは非決定的な値を再現する | **再現しない。記録を読み直すだけ** |
| ④ | ステップは出力が終われば完了 | **履歴に記録されて初めて完了** |
| ⑤ | LLM を決定論的にする | **LLM は非決定的のまま。**リプレイが決定論的になる |
| ⑥ | ワークフローは人間か AI のどちらかが決める | **人間が地図、AI が経路** |
| ⑦ | ブラックボックスだから LLM は扱いにくい | **むしろ逆。**隠れた非決定性のほうが危険 |

## 14. まとめ

### 一枚で言うと

```
durable execution は…
  ✕ LLMを決定論的にする道具        → LLMは非決定的のまま
  ✕ データの正しさを保証する道具     → 保証するのは実行の完遂
  ✕ トークン節約ツール              → それは副次効果
  ✓ 一度出た答えを二度と聞き直さず、
    処理を必ず最後まで完遂させる仕組み
```

### 覚えておくとよいこと

1. **一番危険なのは失敗ではなく、中途半端な成功。** 静かにデータ整合性を壊す
2. **非決定性は消さない。一度きりに閉じ込める**
3. **Workflow は決定論的、Activity は非決定的。** この分離が全ての土台
4. **ステップの完了は「記録されたとき」。** 結果が手元にあるだけでは足りない
5. **冪等性は依然として自分の仕事。** at-least-once であることを忘れない
6. **人間が可能性の空間を定義し、AI がその中の一本の道を選ぶ**
7. **実行中の処理があるコードは気軽に変えられない。** バージョニングが最大の運用課題
